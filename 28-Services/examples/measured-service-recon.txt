READ THE NUMBERS PROPERLY
-------------------------

325 OPEN services across 94 packages on a stock, unmodified consumer phone is
NOT a claim that this device has 325 vulnerabilities. It is a claim that 325
services on this device will accept a bind from an app that asked for no
permissions at all. Most of them will hand back an interface that does nothing
useful to an attacker. A few will not. Finding out which is the job, and there
is no shortcut: you bind, you read the descriptor, you look at what the methods
do. README section 5.7 is the rubric.

The counts that actually mean something to a defender:

  SYSTEM-BIND 76   Correct use of the platform's own pattern: exported=true so
                   the system can bind, guarded by a BIND_* permission only the
                   system holds. Every one of these is a control observed, not a
                   finding. 9 of them are accessibility services.

  SIGNATURE   108  Exported behind a signature-level permission. You need the
                   vendor's key. Also correct.

  NOT-EXPORTED 287 Not reachable from another uid at all.

  DISABLED    24   enabled=false. Note that the owning app can re-enable any of
                   these at runtime with setComponentEnabledSetting, so a
                   manifest-only or dumpsys-only review can be wrong about them.

Five of the sixteen are guarded by android.permission.INTERNET. INTERNET is
protectionLevel=normal and is held by essentially every app on the device, so as
a service guard it is exactly equivalent to no guard at all. It is not a
mistake anyone makes on purpose; it happens when a developer copies
android:permission from a <uses-permission> line. README section 5.3.3.

The others are custom permissions declared at `normal`, which is the same
mistake with the app's own name on it: any app can hold
com.android.vending.CHECK_LICENSE by adding one <uses-permission> line.

AND WHY THAT ONE IS *NOT* A FINDING -- MEASURED
-----------------------------------------------

KeyChainService looks alarming in the table: OPEN, no permission, and it is the
system credential store. So it was bound from an unprivileged app (uid 10291):

    BIND-RETURN com.android.keychain/com.android.keychain.KeyChainService => true
    ... and onServiceConnected NEVER FIRED.

bindService returned true and the connection was never established, because
KeyChainService.onBind returns a binder only for the action it recognises and
null for anything else. A tester who recorded the `true` and moved on would have
filed a critical finding against a service they could not actually reach.

This is the single most useful row in the whole capture, and it is why the
script's own summary says OPEN is a work queue. The table gets you to the door.
Only onServiceConnected tells you the door opened.
