real services on a physical device.

Every measurement below is verbatim. The one edit made before committing is to
package NAMES: assessed third-party applications are written
`com.vendor.<category>`, per 72-RealWorldFindings/references/README.md section 4.
Platform and OEM system packages keep their real names -- they are the operating
system under test, and no verdict here is attached to any of them.

WHAT EACH OF THE FOUR TAUGHT
----------------------------

VaultService          THE FULL CHAIN. bind -> descriptor -> token -> secret, in
                      about twenty lines of attacker code, from an app with one
                      permission. Note the two log lines from the VICTIM: onBind
                      saw callingUid=10310 (its OWN uid) while getAuthToken saw
                      uid=10313 (the real attacker). Same connection, two
                      different answers, one millisecond apart. That is
                      README section 3.7 and it is the reason the vulnerable
                      version's onBind check is inert.

KeyChainService       bindService returned TRUE and onServiceConnected NEVER
                      FIRED. Its onBind returns a binder only for the action it
                      expects and null otherwise, and we sent a bare component
                      Intent. A tester who recorded the `true` and stopped would
                      have filed a critical finding against the system
                      credential store based on a connection that never existed.
                      service-recon.py rates this service OPEN, correctly, and
                      says in its own summary that OPEN is a work queue.

MiuiWifiService       The permission gate working. It is guarded by
                      com.xiaomi.permission.ACCESS_WIFI, protectionLevel
                      signature, so the refusal is loud and specific. This is a
                      CONTROL OBSERVED, not a finding, and it belongs in the
                      report as one.

AnalyticsService      A real vendor service, reached and called. The blind
                      probe at codes 1-3 with an empty parcel produced
                      "Binder invocation to an incorrect interface" three times,
                      which is how you know it is an AIDL Stub rather than a raw
                      Binder. Writing the descriptor it had already given us
                      (com.miui.analytics.ICore) got past enforceInterface, and
                      codes 1 and 3 then executed and returned. Whether anything
                      those methods do is worth reporting is a separate
                      question. Reaching them was free.

TWO CONCLUSIONS, BOTH OF WHICH CHANGE HOW YOU TEST

1.  A bare `false` with no exception is package visibility, not a control. If
    you do not know this, you will write "not reachable" about services that are
    wide open. On API 30+ this is the single most likely cause of a false
    negative in service testing.

2.  descriptor='' means the object is a RAW Binder, not an AIDL Stub. Nothing
    enforces an interface token, so every transaction code is reachable with an
    empty parcel, and `ok=false` here simply means the default onTransact did
    not handle codes 1-3. Those are the services worth sweeping properly,
    because there is no token to get right and no generated Stub to read.

================================================================================
FOR THE REPORT: WHAT THIS DOES AND DOES NOT PROVE
================================================================================

PROVES   An unprivileged, permission-free third-party app can bind an exported
         service in another app and invoke its methods, and the service sees the
         attacker's true uid and does nothing with it.

PROVES   The interface descriptor is disclosed to any caller on request, so
         "the interface is not documented" is not a control.

PROVES   A caller check written in onBind() compares the app against itself.

DOES NOT PROVE anything about the three real device services beyond
         reachability. Reaching com.miui.analytics.ICore is not a finding; what
         its methods do would have to be established by reading the APK. The
         chapter deliberately stops there.

DOES NOT PROVE that this generalises to API 31+ devices unchanged. Package
         visibility, background start rules and foregroundServiceType all
         changed after API 30 and this device cannot exhibit those changes.
